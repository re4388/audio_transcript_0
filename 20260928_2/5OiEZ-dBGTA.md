## 一句話總結
面試多家「業務完全不同」的公司，問題卻收斂到同一套能力——**Agent 工程師 ≈ AI-native Software Engineer**：你不能只懂 LLM，也不能丟掉後端；重點是用可靠的軟體系統，把 LLM 的不確定性包起來。

## 核心論點
1. **面試趨勢變化**：4 月時多數面試官還只問 RAG／LangChain／prompt 這些基礎；到秋招，問題明顯變難——RAG 文檔怎麼切、為什麼這麼切、向量資料庫怎麼選、數據量擴大怎麼辦、為什麼要 Multi-Agent、一個普通 chain 不行嗎、LangGraph 的 state 怎麼存、Kafka 消息堆積／為什麼對接……還有現場 AI Coding（Cursor 類環境，40 多分鐘做系統設計題）。
2. **面試官對 Agent 項目已「祛魅」**：不在乎你用了多少框架，更在乎**你為什麼用**。若說不出「為什麼要 Multi-Agent」，前面堆的技術名詞在面試官眼裡只是炫技。
3. **什麼是 Agent（四字框架：感知、決策、執行、歸一）**：Agent **完全可以沒有聊天介面**——做數據中台的同學那些 Agent 就是企業內部「哨兵」：每天凌晨自動跑性能數據、發現某版本下降、自動定位到圖片加載階段、早上 9 點給群發報告。**企業真正願意付錢的 Agent 不是因為它像人，而是因為它把原本工程師每天重複完成的 workflow 自動化了。**
4. **生產 Agent 的 sub-linear 原則：能確定性的部分就不要交給 LLM**：SQL 查詢是確定的、Python 聚合是確定的、指標變化多少也是確定的，這些沒必要讓 LLM 自由發揮。**LLM 真正適合做的是：理解上下文、選擇路徑、做歸因、生成解釋。**系統可拆成兩層——確定性層（查詢）＋ LLM reasoning 層（歸因）。
5. **Workflow vs. Agent 不是二選一**：一端是完全預編排（穩定可控、但靈活性差、自主性弱），另一端是完全動態編排（靈活、但生產環境危險，規劃出錯會無限循環、成本爆炸）。**較認同的是「受控的自主（controlled autonomy）」：核心業務邏輯用 workflow 控制、關鍵節點設約束，在举步的地方（選工具、取哪些資訊）讓 agent 動態判斷——workflow 提供邊界，agent 在邊界內獲得自主性。**
6. **RAG**：不能只說「按文字切片」，要給出完整前因後果——技術手冊有明顯章節結構（車型→故障碼→故障現象→解決辦法），若每 500 token 一刀切，會把「故障現象」和「解決辦法」拆開、污染 embedding。做法：**structure-aware chunking**（按標題做一級拆分，section 太長再滑動窗口），並保留原數據（metadata）。
7. **向量資料庫選擇考的是 tradeoff**：不是哪個最好，而是**為什麼最適合你這個階段**。例：幾十份記錄手冊、上萬個切片、內部原型、低頻、快速迭代——這根本不需要重型分布式向量庫，輕量方法更合理；未來需多租戶、動態更新、高頻、高可用再換。
8. **LangGraph**：核心是 **State**——不是抽象名字，而是一個整段 Agent 裡不斷被讀取／更新的狀態（用戶 ID、車架號、故障碼、結果……），在不同 node 間流轉。若被追問「Graph 裡有什麼 State」答不出，就容易被看穿細節不足。
9. **為什麼用某個資料庫**：本質在考「你的數據模型和存儲模型是否匹配」——Agent step 動態、每個 workflow 中間結構都可能不同，document store 較自然；但存帳單、帳戶、資金流水就用另一套。
10. **Multi-Agent 何時才合理**（面試殺手題）：至少滿足一些條件——**不同階段需要完全不同的工具、需要不同的 prompt 和上下文、路徑需要動態分支、某節點失敗後要回退、每個角色有清晰的責任邊界**。要證明「你的複雜是業務要求帶來的，而不是你自己創造的」。
11. **Kafka／分散式**（為什麼 Agent 崗一直問後端）：生產 Agent 根本不可能獨立存在——要消費 events、調用十幾個 tool、產生 trace、透過消費隊做 workflow。流量起來時：消息堆積／延遲／重複消息／亂序／exactly-once 做不到時怎麼設計冪等——**這些全是 Agent Engineer 的問題。**
12. **Text-to-SQL**：簡單的是自然語言直接查庫，真正難的是**自然語言的模糊性**（「賣得最好」指銷量最高？銷售額最高？）——**LLM 最大的問題是它特別喜歡猜，而資料庫場景猜錯就是錯**。解法不是把 prompt 寫好，而是：confidence 足夠高就執行，存在明顯模糊就 **clarification（澄清）**。**好的 agent 不應該什麼問題都回答，它應該知道什麼時候執行、什麼時候拒絕、什麼時候澄清——這個能力可能比回答本身更重要。**
13. **AI Coding 面（40 分鐘，Cursor-like）**：面試官看的是**你怎麼使用 AI**——你的角色是 **tech lead**，AI 是 **junior developer**。四個要點：① 你自己先理解問題（不要第一反應就問 AI，會放棄自己的思考）；② 會不會拆任務（不同部分一塊塊交給 AI）；③ 會不會驗證 AI（有沒有讀、跑測試、檢查邊界，而不是看到綠色就 accept）；④ 能不能解釋 tradeoff（用這個定義狀態 vs 直接定義，各自優劣）。
14. **Agent 工程的複雜度不在 Agent loop 本身**（ReAct loop 幾十行就寫完），**而在它的「外表問題」**：誰能調、操作與寫操作權限是否一樣、參數合法性檢查、高風險操作要不要二次確認、腳本在哪執行（**LLM 生成的 Python 能不能直接跑在生產機？當然不能→沙盒**）。沙盒把生成的代碼丟進隔離環境、超時直接殺掉、訪問未授權資源直接拒絕——**這時 Agent 才從 demo 變成 system**。
15. **BI 崗（評估與歸因，最精彩）**：分幾層——價格權重設計、路由細節、**評估與歸因**。核心洞見：**「方案有效」和「skill 有效」是兩件事，中間隔了一層歸因問題。**你去掉 badcase 後，原有的 bad case 消失、監控系統反而抓不到它——「成功會摧毀自己的證據」的悖論。解法：保留 holdout 流量不吃新 skill 做對照、構造回歸測試集定期投放歷史 badcase、看 skill 命中日誌與 case 消失的時間相關性。還有一題：**拿到五個不同 skill/工具有效的 session，怎麼合併成一個對 skill 的優化方向**——本質是「你優化的究竟是軌跡還是 skill」。

## 關鍵洞察（六層能力模型）
1. **會不會用 LLM**：prompt、structured output、tool calling 等基本模型能力（最低層）。
2. **能否給 LLM 正確資訊**：RAG 系統、chunk、embedding、rerank、context management。
3. **能否控制 LLM 的行為**：workflow、LangGraph、state machine、multi-agent、routing、planning。
4. **能否把 Agent 接到真實世界**：MCP、API、database、cache 等。
5. **你的 Agent 犯錯怎麼辦**。
6. **你怎麼證明這個 Agent 真的有價值**（多數面試官非常 care——企業做不做一個項目取決於其可行性與價值程度）。

## 面試 Tips
- **不要為了 Agent 而 Agent**：能一個 chain／一個 SQL／一個 script 解決就用它——LLM 是系統裡最貴、最慢、最不穩定的組件之一，不是越多越好。現在許多方案都在做「減重」。
- **所有技術選型都要準備「為什麼」**：不只「我用了這個」，而是「為什麼是這個、為什麼不是別的、什麼時候會切換」。知其然，並知其所以然。
- **傳統後端不能丟**：Agent 不是飄在空中的，它最終是一個分散式系統。
- **學會說「不確定」**：領域變化太快，遇到沒做過的就與面試官交流你的看法與可能的 tradeoff，而不是硬往項目上加（會有很多漏洞與不可行性）。
- **學會與 AI 一起工作**：以後很多 SWE 的工作會變成——你定義任務、拆任務、做架構、定驗收，AI 負責生成與搜索。Coding interview 也可能從「你能不能一個人寫完所有代碼」變成「當所有人都有 AI 時，你能不能比別人做出更可靠的系統」。
- **不要只追最新的 LLM 熱點，也要看「八股」**：Agent 最終跑在軟體系統裡，需要服務化、高可用、儲存、網路、監控、部署。
