## 核心論點

AI 把「寫程式」的稀缺性打下來，工程師的價值必須往上游移動：**規格、驗收標準、複雜技術決策**。軟工方法論（TDD、BDD、DDD）在 AI 時代的真正作用不是流程儀式，而是**把 AI 的注意力拆細**，讓产出更可靠。價值＝稀缺性，這是全場的主軸。

## 一、價值與上下游

- **價值定義＝稀缺性**：企業願意付錢，是因為你解決的問題跟錢有關，而且市場上少人會。
- 軟體開發分上下游：下游是 code、架構；上游是驗收標準、複雜技術決策、規格。
- AI 的海嘯從下游來（code 生成），所以人必須往上游走。往上游會撞到 PM/BA，心裡不舒服，但工程師有獨特優勢。
- 工程師的護城河：**可落地的抽象能力**。寫規格時腦袋能同時想著程式碼（data model、API model、功能規則、自動化測試），這是 PM 做不到的，也是這一代工程師還來得及培養的。
- 下一代可能像我們不會寫組合語言一樣，不再具備這種抽象能力——所以現在是「末班車」。

## 二、四個 D：先分清楚誰不是方法論

- **SDD（Spec-Driven Development）不是方法論**：它是 OpenAI 2024 年為教育市場提出的概念——不要把需求散在對話框裡下 prompt，而是先寫清楚 spec，再交給 AI coding。
- 當時技術幾乎做不到，所以本質上是「寫完規格，祈禱 AI 一次做對」。
- 作者同意大方向，但認為只停在這個層次太無聊；真正的方法論是下面三個，目的是**盡可能提高 SDD 的正確率**。

## 三、TDD／BDD／DDD 的統一解釋：拆注意力

- LLM 的機制是注意力（Attention is all you need）。你只給 spec 和 code，注意力不會分配到中間階段，AI 就會眼高手低、一次做太多。
- **TDD**：spec → test → code。加自動化測試，把注意力拆開。
- **BDD**：再加 Gherkin（連 PM 都看得懂的測試描述），注意力再細一層。
- **DDD**：再加 domain model（領域模型：財務、商品等領域的知識與規則），讓寫規格時就有領域概念。
- 一句話：**方法論就是拆注意力，拆得越細，LLM 越可靠。**

## 四、Skill 與 Agent Skills

- 「Skill.md」講得不精準；正確是 Anthropic 的 **agent skill**：一個資料夾、多個檔案，把 prompt 模組化。
- 最笨但可行的分法：**一個產出物一個 skill**。SDD 有兩個產出物（規格、程式碼），就兩個 skill。
- 值得長期投資：把「怎麼寫好規格」整理成自己專屬的 skill，職涯中可重複使用。
- 要全自動或高可靠，關鍵是好好投資自己的 skills，而不是追哪個模型比較強。

## 五、方法論的選用時機：看產品生命週期

四個階段：導入期、成長期、成熟期、衰退期。

- **導入期**：公司在探索市場，核心功能隨時會改。用再多工程技巧保護程式碼也沒用；此時最重要的是業務，工程師不必上太多方法論，SDD 提升效率即可。
- **成長期**：流量起來，核心功能要保護，必須 test first（TDD 或 BDD），否則專案一定完蛋。
- **成熟期**：重點是高效率維護，同樣要自動化測試保護既有功能。
- **衰退期**：能跑就好，工程師該準備跳槽。

補充：不要無腦追求 95% 測試覆蓋率。測試要按需補，判斷依據是功能對產品的意義。

## 六、Kano 模型：哪些功能一定要測

（影片口誤稱 Canal Model，即 Kano Model。）

- **基本門檻（must-be）**：沒有就直接走人。例如筆記 App 的筆記功能、白板產品的白板功能、金流。這類要有高覆蓋率，甚至做探索式測試。
- **性能（performance）**：做得越好，使用越久、越開心。
- **魅力（attractive）**：有做會讓使用者「哇」一下，提高黏著度。

## 七、Code Review 還要做嗎？

- 把 AI 當下屬帶：你 review 是因為 **trust 問題**，不是每行都看。
- 真正要抓的是：有沒有想清楚、有沒有跨平台問題、模組有沒有拆分（避免長成腫瘤）、效能、團隊一致性。
- 做法：先做 pattern matching，把要檢查的點寫成 **evaluator skill**，用 sub agent（worker 寫、evaluator 吃 skill 評）去跑，可省約九成時間。
- 抓大放小：以前人工 review 也沒解決所有問題，AI review 甚至可能更快更好，多數人缺的是那個 skill 與思維。

## 八、在公司推動 AI BDD 的實務

- 先讓事情變簡單：讓 PM 用一個 skill 就能寫出規格、AI 會主動問問題，隊友自然願意加入。
- 對工程師，賣點不是「規格很重要」，而是**自動化測試**——工程師不會懷疑測試的用處。企業客戶已有幾萬個自動化測試，新功能就是跑通測試、看 AI 表演。
- 最大阻力是**業務**：業務不會配合你的方法論，連董事長都不敢動賺錢的團隊。解法是用科技降低阻力（業務照常開工單，AI 做剩下的），而不是叫業務學 skill。

## 九、知識庫與 Shared Context

- DDD 的假設：協作瓶頸來自語言不同義——programming language、技術術語、PM 行話、QA 測試資料各說各話。
- 解法是建立單一事實來源（single source of truth）與統一的 domain model，讓 AI 與 RD 認知落差變小。
- 2026–2027 的關鍵技術戰場是 **shared context**：把 plan、決策、會議記錄、規格都放在大家共同可讀的地方（他說 GitHub repo 就夠，不必迷信 Confluence）。
- 若 context 只累積在個人終端機，認知負擔無解；反之，AI 能從一個決策連到會議記錄、程式碼、別人的 API，產生「認知超前」。

## 十、模型智商怎麼分配

- **瓶頸轉移**：AI 笨的時候瓶頸在程式碼；現在瓶頸在測試與規格。
- 左側（寫自動化測試、架構標準、review）用**最高智商模型**；右側（依測試實作）可用便宜模型。
- 實驗：作者寫了數百個自動化測試，用 Cursor 最便宜的 Auto 模型跑兩天，測試全過，遊戲只有約兩個 bug，而且是他自己沒想到的邊界條件。
- 注意：只通過測試不等於架構正確，所以還需要**架構標準文件**＋高智商模型做語義 review。
- AI 有 **self bias**：叫它自己檢查會自我滿意，所以檢查要用更強的模型。
- 非功能性需求（架構、資源、效能）：先問有沒有成熟工具可自動測；沒有才寫 skill 約束。

## 十一、新人與既有系統

- 新人不清架構就把需求丟給 AI，功能測試會過但架構走鐘——這正是 shared context 要解決的。
- 用 CLAUDE.md／AGENTS.md 把架構規範寫清楚，配合自動化測試，即使模型較笨也能貼近團隊風格。

## 十二、職涯建議（結尾雞湯）

- 工具與技術不是護城河，**人**才是。
- 年薪 100–150 萬在純軟不是遙不可及；企業客戶在搶懂規格、驗收標準與架構的人才，年薪 120 萬以上願意給。
- 做法：列出目前工作不滿意的十點，不要抱怨，逐一解決；每解決一個問題就留下一個 skill，第二個更大的問題會讓 skill 更強。
- 不要一直學別人的東西（P stack、Grill Me 很好，但那不是你的）；用 skill engineering 做出符合自己習慣的東西。
- 累積不超過二十個步驟，競爭力就能名列前茅。

## 一句話總結

AI 會寫程式之後，工程師的價值不在打字速度，而在把需求拆成規格、驗收標準與測試，讓 AI 的注意力被約束住——稀缺的不是程式碼，是能落地的抽象。
