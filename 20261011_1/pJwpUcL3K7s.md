## 一句話總結
OpenAI 推出 Decisions API，把「模糊輸入→明確答案」的判斷層產品化，支援文字與圖像，實測延遲低、成本小。

## Decisions API 是什麼
- 不同於 Chat Completions／Responses 的「產生文字」，也非純結構化輸出；它針對「問題定義明確」的判斷。
- 目前支援三種題型：謂詞（判斷條件真假）、選擇（從固定選項挑選）、評分（依有序等級打分）。
- 會回傳機率；適合放在「模糊輸入」與「確定性業務行為」之間的判斷層。

## 與結構化輸出的差別
- 結構化輸出：讓結果符合你的物件結構（提取訂單號、日期等）。
- Decisions：只處理答案清晰明確的問題；完全確定性的規則（如金額 >1000 觸發人工審核）直接寫程式更合適。
- 權限檢查、付款、刪除、帳號變更不應只依賴單一模型判斷。

## 使用要點
- 端點 POST /v1/decisions；目前唯一可用模型為 GPT-4o。
- 多個獨立問題可共用同一輸入、單一請求送出；若後續問題依賴前一題答案，需拆成兩個請求。
- 回傳答案順序與問題順序一致，但應用最好按名稱查找，並檢查每個問題是否被拒絕。
- 圖像輸入：需 base64 編碼（不接受公開 URL 或檔案 ID），單一請求最多 128 張。
- 建議用輕量適配器層統一處理逾時、錯誤、拒絕與回傳值。

## 實測結果
- 12 個客服工單案例：部門分類 12/12 正確；緊急程度以 0.5 為門檻，11/12 正確（誤判為重複收費案）。
- 延遲 174–557ms，中位數 211ms；12 個請求共 4270 輸入 token，成本約 0.00427 美元。
- 提醒：0.5 不是通用門檻，可用雙門檻（高機率自動、中機率人工審核）。

## 模型路由的澄清
- OpenAI 不在 API 層自動提供候選模型；頂層 model 參數只決定「誰在做決策」。
- 若要路由，候選模型與描述須由開發者提供；描述只影響「選擇」，不會讓模型變強。
- 更安全做法：先用程式碼依權限、工具、預算、資料策略篩選，再讓 Decisions 在「快／平衡／深度」等路徑中選。

## 適用判斷三問
1. 答案可否列舉？
2. 錯誤的代價可否定義？
3. 有了結構後，後續行動是否明確？

內容分類、路由、風險評分、視覺／語音控制通常符合；創意寫作、常規規劃不適合。

## 一句話
模型提供機率，程式做出最終決定；真正要長期維護的是問題、選項標籤、閾值與行動策略。
