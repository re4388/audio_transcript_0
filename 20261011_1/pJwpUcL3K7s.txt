扮演著更為專業的角色。首先提供文字或圖片，然後提出幾個問題，並給出明確的答案。目前支援三種類型的問題。謂詞，用於判斷條件是否為真；選擇，即從固定選項中挑選；並根據有序等級對輸入進行評分。例如，客戶服務工單可以同時詢問應該轉到哪個部門，以及是否需要緊急處理。第一種題型是選擇題。第二個問題是謂詞。此模型傳回每個部門選項的機率以及需要緊急處理的機率。因此，它適合作為模糊輸入和確定性業務行為之間的判斷層；語言和圖像中難以用規則規範的部分可以留給模型來處理。最後，是否應該執行？是否需要送交人工審核？這仍然可以透過程式碼來決定。決策、結構化輸出和規範代碼。它們似乎都能返回結構化的結果，但它們解決的是三個不同的問題。結構化輸出著重於使產生結果與您的物件架構相匹配，適合提取訂單編號、名稱、日期或多欄位結果。決策系統只處理答案清晰明確的問題。   目前，它支援我們剛才提到的幾種類型：謂詞、選擇和分數。它會傳回相關的機率。如果規則是完全確定性的，例如“如果金額超過 1,000 美元，則觸發人工審核”，那麼直接編寫程式碼會更合適。權限檢查、狀態驗證、付款、刪除和帳戶變更不應僅依賴單一模型的判斷。因此，這裡有一個非常重要的考慮因素。正確的回答格式並不代表判斷是正確的。高置信度並不意味著該操作已獲得授權。現在我們來看一個實際的 API 呼叫。我們將打開執行腳本並在終端機中運行它。 Decisions 使用單獨的 POST/v1/decisions 端點。目前，唯一負責此判斷的模型是 GPT-4o。在支援工單範例中，我們將工單文字放入輸入框中。我們在問題欄中輸入了兩個問題。其中一道是選擇題。它負責從帳單、技術和運輸三個選項中選擇一個，而另一個選項是一個布林類型的問題，用於確定工單是否緊急。這兩個問題是互相獨立的。因此，它們可以在單一請求中共享相同的輸入。如果後續問題需要用到前一個問題的答案，那麼應該將其拆分成兩個請求。 API 傳回的答案順序與問題的順序相同。   但是，應用程式最好還是按名稱查找答案。不要完全依賴他們的立場。每個問題都可能導致被拒絕，所以你也必須檢查這一點。   在實際實作中，您可以將這些呼叫封裝到一個輕量級適配器層中。統一處理逾時、錯誤、拒絕和傳回值。這樣，在維護階段，即使 OpenAI 的介面發生變化，您也不需要一次修改所有業務流程。這些都是標準的軟體工程實務。 Decisions API 的許多應用場景都可能提到模型路由。我需要在此澄清，OpenAI 不會在 API 層面上為您提供候選模型。也不會自動讀取特定使用者可以呼叫的型號。請求中的頂級“模型”參數指示誰在執行此決策。目前，這裡只能使用 GPT-4o。如果要使用 Decisions 進行模型路由，則候選模型和每個選項的描述必須由開發人員提供。本質上，這是開發者使用 Decisions建立自己的路由器；它並非 OpenAI 提供的現成功能。這些描述只會影響選擇；他們並沒有改變模型本身。例如，如果你將一個模型描述為擅長複雜推理，決策系統可能會更傾向於選擇它，但模型並不會因此獲得更強的推理能力。如果你的模型描述寫得不正確、過時或過於模糊，結果也會很差，這是你必須特別注意的地方。更安全的方法是使用標準程式碼首先根據權限、工具支援、預算、資料策略等篩選模型，然後讓 Decisions 從應用程式定義的路徑中進行選擇，例如「快速」、「平衡」或「深度」。   最後，使用程式碼將所選路徑對應到特定模型。官方範例也選擇了一個「原因」操作，然後應用程式呼叫推理模型，而不是直接選擇特定的模型 ID。OpenAI Decisions 中的圖像輸入值得單獨強調：根據目前公開的文檔，Decisions API 仍然只接受文字或結構化數據，不支援原生圖像輸入。 OpenAI 的決策API
